# Play-based game design study

> CAVEAT, CARRY VERBATIM: protocol only — in-thread play execution FAILED (browser player kept failing to play properly, user said "Just stop dude", study stopped 2026-11-08). The sheet + protocol are the reusable parts, not the play-execution.

## When to use this skill

- Use it to build a reusable game-design reference library by studying real games, one at a time.

- Use the queue, the Step 0 rule, and the itinerary sheet below; they are the parts that survived.

- Do not promise in-thread browser play as the execution method; that is the part that failed. If play is needed, the execution method must be proven separately first.

## Compile the queue first

- Build a ranked queue from the portal's own category pages: top 10 most-played per category.

- Exclude ads from the queue; an ad is not a game.

- Record honest gaps where a top 10 cannot be verified from the category pages; do not fill gaps with guesses.

- Save the queue as a file before studying any game.

## One game at a time

- Study one game at a time and finish its sheet before starting the next.

- Do not batch games; the sheet is only useful when each game gets a full pass.

- File per-game notes as separate entries so the library grows game by game.

## Step 0: read the game's own How to Play menu first

- Before playing or judging anything, read the game's own How to Play menu: objective, controls, and what the player can do.

- Record the objective and controls in the sheet before any other section.

- Never review a game whose objective you have not read from its own menu.

## Fill the fixed itinerary sheet

- Fill the same fixed sheet for every game so games can be compared across the library.

- Sections: entry and menus, character design, pixel art and graphics, animation, gameplay, camera, specs box, and the hub-versus-game-inside-it distinction.

- Use the sheet template in `templates/itinerary-sheet.md`.

- Refine the sheet in batches when early games expose holes in it; the sheet improves from use, and the refinement itself is part of the method.

## Report honestly

- Report each game as fully studied, PARTIAL, walled, or not-played, and say which.

- Name the blocker plainly when a game cannot be studied: login gate, unplayable frame rate, listing-name mismatch, or anything else that stopped the study.

- Never present a PARTIAL or not-played game as studied.

## Standing rules

- Never claim more than was checked; a game on the queue is not a game studied.

- One game at a time; finish the sheet before moving on.

- When the user says stop, stop.
